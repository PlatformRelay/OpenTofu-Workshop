## Objective

You can author, parameterize, guard, and package a config. Now you learn to
**evolve** one safely. Three questions decide whether a change is calm or violent:

- **`count` vs `for_each`** — how you fan a resource out decides what a *later*
  edit costs. `count` addresses by **index**, so removing a middle element
  renumbers everything after it and forces immutable resources to
  destroy+recreate. `for_each` addresses by **key**, so removing one entry
  touches only that instance.
- **`dynamic` blocks** — the same fan-out one level *deeper*: not "many
  resources" but "many repeated **nested blocks** inside one resource". You will
  write one yourself — and hit the two errors everyone hits on the way.
- **Refactoring blocks** — a `moved` block renames or re-keys a resource **in
  state** without touching real infrastructure, so a refactor plans as a no-op
  instead of a destroy+recreate.

The payoff is a chain of **break → fix** beats: an innocent-looking edit that
silently forces the whole fleet to be re-created, a copy-paste bundle that
*silently forgets* a new service, and a fan-out whose width isn't known at plan
time — each caught in `tofu plan` before any damage, then fixed. You run
**tracked files**, not heredocs — what you apply is exactly what CI verified.

### Continuity — S09 sits beside the stage sequence

S09 carries no stage number in the `service-manifest` map, but it is not outside

> **Scope note (no-Docker):** everything here runs against the pure-local
> `local` and `archive` providers — `local_file` is an **immutable** resource

<!-- source: labs/day-1/09-best-practices/main.tf -->
```hcl
terraform {
  required_providers {
    local   = { source = "hashicorp/local" }
    archive = { source = "hashicorp/archive" }
  }
}

# The services this config renders a manifest for. Each entry is one deployable
# unit, keyed by a stable name — the key, not a list position, is the identity.
variable "services" {
  type = map(object({
    replicas = number
  }))
  default = {
    checkout = { replicas = 2 }
    payments = { replicas = 4 }
    search   = { replicas = 3 }
  }
}

# for_each fan-out: instances are addressed by KEY (manifest["checkout"], …), so
# adding or removing one map entry touches only that instance — the later ones
# keep their identity. This is the removal-stability fix for the count trap.
resource "local_file" "manifest" {
  for_each = var.services

  filename = "${path.module}/out/${each.key}.env"
  content  = <<-EOT
    SERVICE_NAME=${each.key}
    REPLICAS=${each.value.replicas}
  EOT
}

# Refactor without replacement: tell OpenTofu each old count-indexed instance is
# the same object as its new keyed address. Plan resolves to a no-op state move,
# not a destroy+recreate. Indices follow the count form's sorted key order:
# 0=checkout, 1=payments, 2=search.
moved {
  from = local_file.manifest[0]
  to   = local_file.manifest["checkout"]
}

moved {
  from = local_file.manifest[1]
  to   = local_file.manifest["payments"]
}

moved {
  from = local_file.manifest[2]
  to   = local_file.manifest["search"]
}
```

<!-- source: labs/day-1/09-best-practices/bundle.tf -->
```hcl
# The deploy artifact: ONE zip holding every service's manifest.
# (hashicorp/archive is declared in main.tf — a module may carry
# only one required_providers block.)
# "source" is a repeated NESTED BLOCK inside this data source —
# exactly the shape dynamic blocks exist to generate.
data "archive_file" "bundle" {
  type        = "zip"
  output_path = "${path.module}/out/bundle.zip"

  # One source{} per service. The iterator is named after the
  # LABEL: source.key / source.value, not each.key / each.value.
  dynamic "source" {
    for_each = var.services
    content {
      filename = "${source.key}.env"
      content  = "REPLICAS=${source.value.replicas}\n"
    }
  }
}

output "bundle_sha256" {
  description = "Bundle checksum — changes with any manifest."
  value       = data.archive_file.bundle.output_sha256
}
```

## Step 1 — Start from `count`: apply three services

To see the trap you have to start where most configs start — a `count` fan-out.
**Temporarily** replace `main.tf` with the `count` form. Copy this whole block
over the file:

```hcl
# TEMPORARY (Step 1 starting point) — the count form, addressed by INDEX.
terraform {
  required_providers {
    local = { source = "hashicorp/local" }
  }
}

variable "services" {
  type = map(object({
    replicas = number
  }))
  default = {
    checkout = { replicas = 2 }
    payments = { replicas = 4 }
    search   = { replicas = 3 }
  }
}

# count only knows "how many". To fan out over NAMED things you must
# flatten the map into an ordered list and index back into it — the
# gymnastics are part of the lesson.
locals {
  service_names = sort(keys(var.services))
}

# count-based fan-out: instances are addressed by INDEX (manifest[0], [1], [2]).
resource "local_file" "manifest" {
  count = length(local.service_names)

  filename = "${path.module}/out/${local.service_names[count.index]}.env"
  content  = <<-EOT
    SERVICE_NAME=${local.service_names[count.index]}
    REPLICAS=${var.services[local.service_names[count.index]].replicas}
  EOT
}
```

(The temporary form doesn't re-declare the `archive` provider — `bundle.tf`'s
data source still resolves it implicitly as `hashicorp/archive`.)

Then init and apply:

```bash
tofu init
tofu apply -auto-approve
tofu state list
```

**addressed** in state? What extra entry rides along?

<details><summary>Solution / expected output</summary>

```console
$ tofu plan
...

-/+ resource "local_file" "manifest" {
      ~ content              = <<-EOT # forces replacement
          - SERVICE_NAME=payments
          - REPLICAS=4
          + SERVICE_NAME=search
          + REPLICAS=3
        EOT
      ~ filename             = "./out/payments.env" -> "./out/search.env" # forces replacement
...
  # local_file.manifest[2] will be destroyed
  # (because index [2] is out of range for count)
...
Plan: 1 to add, 0 to change, 2 to destroy.

Changes to Outputs:
  ~ bundle_sha256 = "98817fde81e5659f696dcd4e2fc4a0ee7a9add23359b83f09e5cdec82e2763a6" -> "f06846170b3fa7a1c4be0b4fff081a35bbb476e8b53af3d40b40224685843b46"
```

You removed **one** service but the plan is `1 to add, 0 to change, **2 to
destroy**`. Because sorted keys shift down, `manifest[1]` — formerly *payments*
— is now recomputed as *search* and **must be replaced** (its `filename` and
`content` change, and `local_file` is immutable), while `manifest[2]` is
**destroyed** for being out of range. The service you *kept*, `search`, gets
churned; the index is a position, not an identity. (The `bundle_sha256` output
also changes — the dynamic bundle you'll study in Step 6 correctly drops
`payments.env`.) **Do not apply** — revert `payments` back into the map first:

```hcl
  default = {
    checkout = { replicas = 2 }
    payments = { replicas = 4 }
    search   = { replicas = 3 }
  }
```

```console
$ tofu apply -auto-approve
No changes. Your infrastructure matches the configuration.

Apply complete! Resources: 0 added, 0 changed, 0 destroyed.
```

## Step 3 — Refactor to `for_each` **without replacement** using `moved`

Now fix the design. Restore the tracked canonical `main.tf` — the `for_each` end
state with the three `moved` blocks:

```bash
git checkout -- main.tf
```

`for_each` addresses instances by a **stable key** (`manifest["payments"]`)
instead of a shifting index. But switching a resource from `count` to `for_each`
normally looks like a *different* resource to OpenTofu — the addresses changed
(`manifest[0]` → `manifest["checkout"]`) — so without help it would destroy all
three and recreate them. The three `moved` blocks tell OpenTofu that each old
address **is** the new one: rename in state, touch nothing real.

```bash
tofu plan
```

**Task:** The addresses all changed from index to key. How many resources does
the plan add, change, or destroy — and what does OpenTofu report instead?

<details><summary>Solution / expected output</summary>

```console
$ tofu plan
...
  # local_file.manifest[0] has moved to local_file.manifest["checkout"]
  # local_file.manifest[1] has moved to local_file.manifest["payments"]
  # local_file.manifest[2] has moved to local_file.manifest["search"]
...
Plan: 0 to add, 0 to change, 0 to destroy.
```

**`0 to add, 0 to change, 0 to destroy`** — every instance is reported as
`has moved to`, a pure state rename. Nothing on disk is recreated. That is the
entire point of a `moved` block: it decouples "I renamed/re-keyed this in my
code" from "I want to rebuild this in the world."

Apply it to commit the state move:

```console
$ tofu apply -auto-approve
  # local_file.manifest[0] has moved to local_file.manifest["checkout"]
  # local_file.manifest[1] has moved to local_file.manifest["payments"]
  # local_file.manifest[2] has moved to local_file.manifest["search"]

Apply complete! Resources: 0 added, 0 changed, 0 destroyed.

$ tofu state list
data.archive_file.bundle
local_file.manifest["checkout"]
local_file.manifest["payments"]
local_file.manifest["search"]
```

State is now **keyed by name**, and no file was rewritten.
</details>

## Step 5 — Break → fix: an edit that silently forces a re-create

Not every replacement is as loud as deleting a resource. `local_file` is

it must destroy the old one and create a new one. Say you "tidy up" the
extension from `.env` to `.conf`. **Temporarily** change that one line in
`main.tf`:

```hcl
  filename = "${path.module}/out/${each.key}.conf"
```

Then plan — **do not apply**:

```bash
tofu plan
```

**Task:** You changed one word. What does the plan want to do to the **whole
fleet**, and which line does OpenTofu flag as the cause?

<details><summary>Solution / expected output</summary>

```console
$ tofu plan
...
  # local_file.manifest["checkout"] must be replaced
      ~ filename             = "./out/checkout.env" -> "./out/checkout.conf" # forces replacement
  # local_file.manifest["payments"] must be replaced
      ~ filename             = "./out/payments.env" -> "./out/payments.conf" # forces replacement

      ~ filename             = "./out/search.env" -> "./out/search.conf" # forces replacement
```

`Plan: 3 to add, 0 to change, **3 to destroy**` — a one-word cosmetic change

## Step 6 — Meet the `dynamic` block: fan-out one level deeper

`for_each` on a resource answers "how many **resources**?". Some arguments are
themselves **repeated nested blocks** — a security group's `ingress` rules, an
IAM policy's `statement`s, and here `archive_file`'s `source {}` entries. A
**`dynamic` block** answers "how many **nested blocks** inside this one
resource?".

Read `bundle.tf` (shown in *Files used* above), then inspect what it has been
quietly maintaining all along:

```bash
tofu output bundle_sha256
unzip -l out/bundle.zip
unzip -p out/bundle.zip checkout.env
```

**Task:** How many entries does the bundle hold, and where did each come from?
In the `dynamic` block, what is the iterator called — and why not `each`?

<details><summary>Solution / expected output</summary>

```console
$ tofu output bundle_sha256
"98817fde81e5659f696dcd4e2fc4a0ee7a9add23359b83f09e5cdec82e2763a6"

$ unzip -l out/bundle.zip
Archive:  out/bundle.zip
  Length      Date    Time    Name
---------  ---------- -----   ----
       11  00-00-1980 00:00   checkout.env
       11  00-00-1980 00:00   payments.env
       11  00-00-1980 00:00   search.env
---------                     -------
       33                     3 files

$ unzip -p out/bundle.zip checkout.env
REPLICAS=2
```

Three zip entries, one per `var.services` key — each generated by one iteration
of `dynamic "source"`. Read the block as: the **label** (`"source"`) names the
nested block type to synthesise; `for_each` feeds it a collection; each
`content {}` stamps out one block. The iterator is named **after the label** —
`source.key` / `source.value` — *not* `each.key`/`each.value`; you will feel why
that matters in Step 8. (No `unzip` on your machine? The `bundle_sha256` output
and Step 8's plan diffs carry the same evidence.)
</details>

## Step 7 — Feel the smell: the copy-paste bundle

To appreciate what `dynamic` buys, regress it. **Temporarily** replace the whole
of `bundle.tf` with the hand-written form:

```hcl
# TEMPORARY (Step 7) — the copy-paste form: one hand-written source{}
# per service, with each replica count retyped by hand.
data "archive_file" "bundle" {
  type        = "zip"
  output_path = "${path.module}/out/bundle.zip"

  source {
    filename = "checkout.env"
    content  = "REPLICAS=2\n"
  }
  source {
    filename = "payments.env"
    content  = "REPLICAS=4\n"
  }
  source {
    filename = "search.env"
    content  = "REPLICAS=3\n"
  }
}

output "bundle_sha256" {
  description = "Bundle checksum — changes with any manifest."
  value       = data.archive_file.bundle.output_sha256
}
```

```bash
tofu plan
```

**Task:** The dynamic block is gone and three literal blocks stand in its place.
What does the plan say — and what does that tell you about what `dynamic`
actually *is*?

<details><summary>Solution / expected output</summary>

```console
$ tofu plan
data.archive_file.bundle: Reading...
data.archive_file.bundle: Read complete after 0s [id=624f9bc013ee78d910d2745bf26135683eeb9ea8]

No changes. Your infrastructure matches the configuration.
```

**`No changes`** — the three literal blocks expand to *exactly* what the
`dynamic` block generated (same entries, same order: `for_each` over a map
iterates in sorted-key order), so the zip is byte-identical. A `dynamic` block
is pure **authoring-time sugar**: the provider only ever sees the expanded
nested blocks. Refactoring between the two forms is invisible to the plan —
which also means `dynamic` is never *required*, only *earned*.
</details>

## Step 8 — Write the `dynamic` block yourself (and hit the classic error)

Fix the smell by re-deriving the tracked form **by hand** — don't `git checkout`
yet. Delete the three literal `source {}` blocks and generate them from
`var.services` instead. Almost everyone's first attempt reuses the iterator name
they just learned on resources — try it deliberately:

```hcl
  dynamic "source" {
    for_each = var.services
    content {
      filename = "${each.key}.env"
      content  = "REPLICAS=${each.value.replicas}\n"
    }
  }
```

## Step 9 — The other fan-out trap: width unknown at plan time

`count` and `for_each` share one hard rule: OpenTofu must know **how many**
(and, for `for_each`, **which keys**) at *plan* time. Derive the width from
another resource's computed attribute and planning itself breaks. The real-world
shape of this mistake is `count = length(module.network.subnet_ids)`; here is
its minimal pure-local reproduction. Create a **temporary** scratch file
`receipts.tf` (it is gitignored, like `broken.tf` in earlier labs):

```hcl
# TEMPORARY (Step 9) — a fan-out whose width depends on a value that
# only exists after apply. The real-world shape of this mistake is
# count = length(module.network.subnet_ids); this is its minimal
# pure-local reproduction.
resource "local_file" "audit" {
  filename = "${path.module}/out/audit.log"
  content  = join("\n", [for k, s in var.services : "${k}=${s.replicas}"])
}

resource "local_file" "receipt" {
  count    = length(local_file.audit.content_sha256)
  filename = "${path.module}/out/receipt-${count.index}.txt"
  content  = "ok\n"
}
```

```bash
tofu plan
```

apply. What does OpenTofu refuse to do, and what *two* ways out does the error

## Expected observations

- **`count` addresses by index.** Removing a middle element renumbers every
  later instance; for an immutable resource that means `must be replaced` +
  `will be destroyed` — Step 2 removed one service and planned `2 to destroy`.
- **`for_each` addresses by key.** The identical removal touches only the
  removed key — Step 4 planned `1 to destroy`, and the surviving instances
  weren't in the plan at all. Mis-key that map and the plan fails loudly:
  `Invalid index … The given key does not identify an element`. Prefer
  `for_each` whenever instances have a stable identity.
- **`moved` refactors state, not infrastructure.** Switching `count` →
  `for_each` with `moved` blocks planned `0 to add, 0 to change, 0 to destroy`,
  every instance reported `has moved to` — a state rename, nothing rebuilt.
- **`dynamic` generates repeated nested blocks — and its iterator is the
  label.** The copy-paste bundle planned `No changes` (dynamic is pure
  expansion sugar) but *silently* forgot a new service; the dynamic form updated
  the zip and the checksum output in the same plan that added the instance.
  Writing `each.*` inside a `dynamic` block is the classic first error —
  `The "each" object can be used only in "module" or "resource" blocks`.
- **Fan-out width must be known at plan time.** `count` fed a computed attribute
  fails with `Invalid count argument`; the error suggests `-exclude` (1.9+) as a
  two-pass workaround, but the fix is deriving width from configuration.
- **`plan` is the safety gate.** A cosmetic `filename` edit planned
  `3 to destroy` with `# forces replacement` on the offending line — caught
  before apply. Read the action counts and the `forces replacement` annotations
  every time.

## Stretch (optional)

- **`for_each` over the objects, not just keys.** The map values here carry only
  `replicas`. Add a `tier` field, reference `each.value.tier` in the manifest
  *and* `source.value.tier` in the bundle — one field added to the input flows
  through both fan-outs, resource-level and nested-block-level.
- **Chain two `moved` blocks.** Rename the resource *and* re-key it in one
  refactor (e.g. `local_file.manifest[0]` → `local_file.service_env["checkout"]`)
  and confirm the plan is still `0 to destroy`. `moved` blocks compose — a
  resource can travel several renames across releases and stay a single object
  in state.
- **Name the iterator explicitly.** Add `iterator = svc` to the `dynamic` block
  and switch the references to `svc.key` / `svc.value.replicas` — useful when
  nesting would shadow a label. Confirm the plan stays `No changes`, then revert.
- **Contrast with `removed`.** On the slides you saw the `removed` block: it
  drops a resource from state *without* destroying the real object (the safe
  successor to `state rm`). Reason about when you'd reach for `removed` versus
  simply deleting a `for_each` key — the difference is whether you want the
  underlying object gone or merely un-managed.
